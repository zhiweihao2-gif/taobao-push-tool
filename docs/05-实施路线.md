# 05 · 实施路线与工程约束

## 1. 里程碑拆解

### M1 · 单平台采集闭环（5–7 天）

**目标**：`python run_demo.py --platform taobao --id xxx` 输出一份完整商品包。

| 任务 | 产出 | 验收 |
|---|---|---|
| mtop 客户端 | `src/collect/mtop.py` | 能稳定拿到 token 并成功调 `pcdetail` |
| 淘宝采集器 | `src/collect/taobao.py` | 标题/主图/SKU/参数/详情图 URL 全齐 |
| 京东采集器 | `src/collect/jd.py` | 同上（无需登录态） |
| 1688 采集器 | `src/collect/alibaba.py` | 同上 |
| 归一化 | `src/normalize/normalizer.py` | 三平台输出同一 `Item` 结构 |
| 图片管道 | `src/media/downloader.py` | 并发下载、去尺寸后缀、落盘 + manifest |
| 命令行 | `run_demo.py` | 端到端跑通 |

**风险点**：token 刷新逻辑、`apiStack` 结构差异、图片后缀规则。

---

### M2 · 映射 + 发布到草稿（10–15 天，最关键）

| 任务 | 产出 | 验收 |
|---|---|---|
| 类目树落库 | `data/category_tree/{platform}.json` | 全量类目可本地查询 |
| 属性元数据缓存 | `data/props/{platform}/{cid}.json` | 含必填标记 |
| 类目映射器 | `src/normalize/category_mapper.py` | Top-5 候选 + 相似度打分 |
| 属性/SKU 映射 | `src/normalize/mapper.py` | 单商品映射准确率 ≥ 90% |
| 文案清洗 | `src/normalize/sanitizer.py` | 极限词命中率 100% |
| 发布器（草稿模式） | `src/publish/taobao_pub.py` | 20 个商品成功进草稿箱 |
| 人工确认界面 | `src/api/main.py` + 简单前端 | 未命中映射可点选 |

**这是项目成败点**：不要指望一次映射全对，必须设计"人工确认 → 写回映射表 → 永久复用"的闭环。

---

### M3 · 批量化与后台（10 天）

- 任务队列 + 失败重试 + 死信
- 多店铺/多账号管理（Cookie 池、限速桶、日配额）
- Web 后台：链接批量粘贴 → 采集 → 预览 → 勾选 → 发布 → 结果列表
- 采集结果 diff：源商品改价/改图后能感知（定时回采 + hash 比对）

---

### M4 · 多平台互铺与运营增强（10–15 天）

- 1688 → 淘宝（最常见场景：找货代发）
- 淘宝 → 京东 / 拼多多 / 抖音小店
- 价格策略引擎（按类目/按销量/按竞品）
- 违规词库自动更新
- 上架后监控：被下架/被投诉/流量异常告警

## 2. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.12 | 爬虫/数据处理生态最全 |
| HTTP | `httpx`（同步 + 异步） | 支持 HTTP/2、连接池、Cookie 自动管理 |
| 解析 | `lxml` + 正则 | 比 BeautifulSoup 快，容错够 |
| 图片 | `Pillow` | 尺寸校验、缩放、水印检测、EXIF 清理 |
| 模型 | `pydantic v2` | 强类型 + 校验 + JSON Schema 导出 |
| 服务 | `FastAPI` + `uvicorn` | 自带 OpenAPI，前端好接 |
| 存储 | SQLite（起步）→ PostgreSQL | 单机零依赖，后续平滑迁移 |
| 队列 | SQLite 表（起步）→ Redis + Celery | 千级以内不需要 Redis |
| 浏览器 | `Playwright`（仅登录/滑块时用） | 不要用它做批量采集，太慢 |
| 前端 | Vue3 + Element Plus 或纯 HTML+HTMX | 内部工具，够用即可 |

**不要做的事**：
- 不要用 Selenium/Playwright 做批量采集（10 倍资源消耗，且照样被风控）
- 不要一开始就上微服务/消息队列（单机 SQLite 能跑 5000 条/天）
- 不要把解析逻辑写死在采集器里（先存 raw，解析可重跑）

## 3. 工程约束清单（这些不做，工具上线即废）

### 3.1 账号与风控
- **采集账号和发布账号必须分离**。采集用小号，封了换；发布用店铺主号，绝不能高频。
- 单账号 QPS 硬限制：淘宝/1688 ≤ 1，京东 ≤ 3，发布接口 ≤ 0.2。
- 每个账号独立 Cookie 文件，独立失败计数，连续失败 5 次自动停用 + 告警。
- 采集时段模拟人工：9:00–23:00，随机间隔 ±40%。

### 3.2 图片
- **必须转存**。直链引用外站图片 = 平台判定外链，且源卖家删图你的商品就变空图。
- 转存后清 EXIF（含 GPS/相机信息，暴露来源）。
- 主图尺寸：淘宝要求 ≥ 800×800 且 1:1；京东 ≥ 800×800。小于的自动放大（Lanczos）并记录。
- 检测水印：源图常见店铺名/二维码水印。简单方案——裁掉底部 8% / 右侧 10%；进阶方案——OCR 检测文字区域。
- 主图视频：`mtop.taobao.pcdetail` 里 `item.video` 有 mp4 直链，同样要转存。

### 3.3 文案
- 极限词（广告法）：「最」「第一」「国家级」「顶级」「绝无仅有」「史上最低」——命中即删。
- 品牌词：无授权不得出现在标题/详情/图片。用黑名单 + 品牌白名单双向校验。
- 联系方式：手机号、微信、QQ 一律剔除（平台判定站外引流）。
- 详情图里的"XX旗舰店"字样同样要处理，否则等于给源店铺打广告。

### 3.4 数据一致性
- 源商品改价后，你的售价不会自动变 → 需要定时回采 + 阈值告警（源价涨 10% 就提醒）。
- 源商品下架/删除 → 你的商品变死链 → 回采时标记 `source_gone`。
- 建议给每个铺货商品存 `source_platform + source_item_id + source_hash`，形成可追溯关系。

### 3.5 平台规则现实（工程事实，不是建议）
- 同一店铺短时间内大量上架结构相似的商品，会被判"重复铺货"，轻则降权重则扣分。
  → 工程对策：上架节奏打散（每小时 ≤ 20 个）、标题/主图做差异化、错开类目。
- 图片与源店铺完全一致会被图片指纹比对识别。
  → 工程对策：重新裁剪/加边框/调色/换首图，做图片差异化。
- 采集端被封的是账号，发布端被罚的是店铺。两者风险等级不同，务必分开处理。

## 4. 成本估算

| 项 | 起步（自用） | 规模化（对外服务） |
|---|---|---|
| 服务器 | 1 台 2C4G（¥60/月） | 3–5 台 + 对象存储（¥500/月） |
| 代理 IP | 不需要（低频） | 住宅代理池（¥300–2000/月） |
| 打码/滑块 | 不需要 | 打码平台（¥0.01–0.05/次） |
| 开放平台资质 | 无 | 企业 + 类目授权（部分需保证金） |
| 开发 | 单人 6–8 周 | 2–3 人 3 个月 |

## 5. 最小可行路径（如果你只想先跑起来）

```
Day 1-2: mtop 客户端 + 淘宝采集，命令行输出 JSON
Day 3:   图片下载转存 + 尺寸处理
Day 4-5: 京东采集（无签名，最快出成果）
Day 6-7: 归一化模型统一三平台
Week 2:  类目映射表（先只做你主营的 3-5 个类目）+ 属性映射
Week 3:  淘宝发布到草稿箱，人工复核 20 个商品
Week 4:  批量循环 + 失败重试 + 简单 Web 界面
```

**先只做 3–5 个类目**，把映射表做深做准，再横向扩展。全类目铺开是失败率最高的做法。

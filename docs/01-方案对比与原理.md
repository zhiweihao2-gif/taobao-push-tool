# 01 · 方案对比与原理

## 1. 三条技术路线

### 路线 A：官方开放平台 API

| 平台 | 采集能力 | 发布能力 | 门槛 |
|---|---|---|---|
| 淘宝开放平台 (open.taobao.com) | `taobao.item.get` 只能取**自己店铺**商品；`taobao.items.onsale.get` 同理 | `taobao.item.add` / `taobao.item.add.v2` / `taobao.item.update`；图片走 `taobao.picture.upload` | 企业资质 + 应用审核 + 类目授权（部分类目需品牌授权） |
| 京东宙斯 (jos.jd.com) | `jingdong.ware.read.findWareById` 限自家 | `jingdong.ware.write.add` / `jingdong.ware.write.update` | 商家资质 + 应用签约 |
| 1688 开放平台 (open.1688.com) | `alibaba.offer.get` 限授权 | `alibaba.offer.publish` / `alibaba.offer.edit` | 同上 |

**结论**：开放平台**读不到别人的商品**。它只能解决"发布"这一端，且需要资质。所以：
- 想读任意商品 → 必须逆向（路线 B）
- 想稳定发布 → 优先走开放平台（如果有资质），否则走后台模拟（路线 C）

正规服务商（如某些 ERP）是 **B 采集 + A 发布** 的组合：采集靠爬虫，发布走已授权的 ISV 应用。这就是它们"合规"的原因——合规点在发布端，不在采集端。

### 路线 B：页面 / 接口逆向（采集端标准做法）

分三个层次，稳定性递减、成本递增：

| 层次 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| B1 静态 HTML 解析 | 请求详情页，正则/lxml 提取内嵌 JSON | 最简单，无需签名 | 淘宝/天猫详情页已 SSR 化但有风控页；京东仍可用 |
| B2 内嵌 JSON 提取 | 抓 `window.__INIT_DATA__` / `TShop.Setup()` / `pageConfig` | 数据结构完整，含 SKU 树 | 结构随版本变，需容错 |
| B3 mtop 接口直连 | 自己算 `sign` 调 `h5api.m.taobao.com` | 最稳定、字段最全、可批量 | 需要 `_m_h5_tk` 令牌 + Cookie + 风控对抗 |

**推荐**：B3 为主 + B2 兜底。B3 拿结构化数据，失败时降级到 B2 解析 HTML。

### 路线 C：商家后台协议模拟（发布端主流）

用**自己店铺**的登录态（浏览器 Cookie / 扫码登录持久化的 session），重放后台"发布商品"的 XHR 请求。

- 淘系：`mtop.taobao.item.publish.*` 系列，需要 `_tb_token_`、`_m_h5_tk`、`x5sec`（滑块令牌）
- 京东商家后台：`/ware/addWare` 一类表单提交，需要 `thor` 令牌
- 1688：`/offer/publish.htm` 表单

优点：不需要资质，个人店也能用。缺点：接口随后台改版变化，需要持续维护；同一账号高频操作会触发风控。

## 2. 各平台反爬机制速览

| 平台 | 关键机制 | 应对 |
|---|---|---|
| 淘宝/天猫 | `_m_h5_tk` 令牌 + `sign=md5(token&t&appKey&data)`；`x5sec` 滑块；`_tb_token_`；UA/设备指纹 | 先请求拿 token（首次必失败），带 token 重签；固定 UA + 合理间隔；登录态复用 |
| 1688 | 同一套 mtop 机制，域名 `h5api.m.1688.com`；另有 `__cn_logon__` 登录态 | 同上，注意 1688 的 `sign` 里 data 需 URL 编码一致 |
| 京东 | 详情页基本无签名；价格/库存走 `p.3.cn` / `c0.3.cn`；移动 API `api.m.jd.com` 有 `sign` | PC 页面 + 三个辅助接口即可，最省事 |
| 通用 | IP 频控、账号维度频控、图片防盗链 | 代理池（可选）、单账号 QPS ≤ 1、图片带 Referer 下载 |

## 3. 为什么"抓下来"不等于"能上架"

一份商品数据从 A 平台到 B 平台，会在这几处断裂：

1. **类目不同**：淘宝叶子类目 `50010850`（连衣裙）在京东是 `1319`，在 1688 是 `1033559`。类目 ID 体系完全独立。
2. **属性体系不同**：淘宝属性 ID `1627207`（颜色）在京东叫 `颜色`，值列表也不同；品牌必须映射到目标平台的品牌 ID（`tb.brand.get` 查询）。
3. **必填项不同**：目标类目有一组"必填属性"，源商品可能根本没填 → 必须补默认值或人工介入。
4. **SKU 结构不同**：源平台是"颜色×尺码"二维，目标平台可能要求"销售属性"最多 3 维且顺序固定。
5. **图片要求不同**：主图数量、尺寸（淘宝要求 ≥800×800）、白底图、是否允许带水印、详情图宽度。
6. **文案风险**：源标题含"正品""官方""最"等极限词/品牌词，直接搬会被判违规下架。

**这 6 条就是"映射层"要解决的问题，也是本项目真正的技术壁垒。**
